# fdoc — FLINT's documentation builder

`fdoc` builds FLINT's documentation (HTML and PDF) from the sources in
`doc/src`. It needs only Python 3.8 or later, with no extra packages.
Node.js is optional: when it is available, all formulas are typeset once at
build time with the vendored KaTeX (and cached in the output directory);
otherwise the pages typeset them in the browser. The PDF needs `pdflatex`
with the usual LaTeX packages (`texlive-latex-extra` on Debian/Ubuntu).

From the top-level directory, after `./configure`:

```
make doc                      # HTML -> build/doc/html (also: make dochtml)
make docpdf                   # PDF  -> build/doc/latex/flint.pdf
make checkdoc                 # check the documentation against the headers,
                              # then compile and run every example program
make doc DOCFLAGS=--redirects # also write redirects for the old (Sphinx) URLs
make doc DOCFLAGS=--strict    # treat warnings as errors (as CI does)
```

Or directly, from `doc/` (after `./configure`):

```
python3 -m fdoc build                 # HTML site -> build/html
python3 -m fdoc build --redirects     # ... plus <old>.html pages that redirect the
                                      # URLs of the old documentation (fmpz.html,
                                      # fmpz.html#c.fmpz_add, ...) to the new pages
python3 -m fdoc build --bundle        # each directory's pages served from one
                                      # <dir>/f.html#name (for hosts that limit
                                      # the number of files)
python3 -m fdoc latex --pdf           # LaTeX + PDF -> build/latex
python3 -m fdoc check                 # documentation vs. headers
python3 -m fdoc examples              # compile and run every example program
                                      # against the in-tree build of FLINT
python3 -m fdoc examples --only fmpz_poly,algorithms/polynomials -v
```

Global options: `--strict` (warnings make the command fail), `-q` (no
progress output; also `FDOC_QUIET=1`), `-j N` (parallel jobs, default the
number of CPUs), `--flint DIR` (the FLINT source tree, default the parent
of `doc/`), `--src DIR` (the documentation sources). `examples` takes
`--cc`, `--cflags` and `--libs` (default: the in-tree headers and library)
and `-v` (also list the examples that pass). Progress is shown on standard
error, as a counter on a terminal and as one line per stage otherwise.

Parsing the sources, scanning FLINT's C sources and headers, rendering and
writing the pages, and compiling and running the examples are done in
parallel (in forked processes; serially where fork is not available). The
output does not depend on the number of jobs.

`fdoc` checks the documentation against FLINT's headers as configured
(some functions are generated by macros that depend on the
configuration), so `./configure` must have been run in the source tree.

The pages do not depend on the configuration, except for the "source"
links of a few functions that are generated by macros. What can be
checked does:

* A module overview can declare `requires: 64` (or `fft_small`, or
  several separated by commas) in its front matter; on a configuration
  without these features (read from `src/flint-config.h`), its functions
  are not checked against the headers, and `check` says so.
* An example can declare `requires=fft_small` (or `64`, `32`) on its
  ```` ```c example ```` line, and `example-requires` in the front matter
  of the home page applies to all examples (it is `64`: the expected
  outputs are those of a 64-bit build). `examples` probes the configured
  build and skips, with the reason, the examples it cannot run.

The HTML pages carry a "Cite this page" box with a citation and a BibTeX
entry. They give the URL under https://flintlib.org/doc/ (the `baseurl`
in `__main__.py`) and the date of the build (`SOURCE_DATE_EPOCH` if set,
for reproducible builds).

A `notice:` in the front matter of the home page (inline markup, may
continue on indented lines) is shown in a box at the top of every HTML
page; it is not included in the PDF. Remove the line to remove the box.

## Files

| Path | Role |
|---|---|
| `fdoc/markup.py` | Parser for the markup dialect below → a plain node tree (shared by all backends) |
| `fdoc/model.py` | Site model: pages, function blocks, symbols, cross-references, numbering, backlinks, header checks |
| `fdoc/csyntax.py` | C prototype parsing, highlighting tokens, source scanner for GitHub links and signature checks |
| `fdoc/html.py` | HTML backend + batched KaTeX pre-rendering (cached in `build/html/.katex-cache.json`) |
| `fdoc/latex.py` | LaTeX backend (one book-style document) |
| `fdoc/redirects.py` | Redirect pages for the URLs of the old Sphinx documentation |
| `fdoc/progress.py` | Progress output |
| `fdoc/static/` | CSS (light/dark), JS (search, theme, mobile nav, citation box, bundles) |
| `fdoc/stubs/` | Header stubs used when expanding FLINT's headers under other architectures' flags |
| `fdoc/vendor/katex/` | KaTeX 0.16.29 (MIT) — JS, CSS, woff2 fonts |
| `src/index.md` | Home page |
| `src/<module>/index.md` | Module overview: every prototype + an essentials-only description |
| `src/<module>/<page>.md` | Hand-written function page (claims functions via `functions:`, all from one section of the overview) or, without `functions:`, a module guide (`summary`, `order`) |
| `src/algorithms/index.md` | Algorithms root (intro; the group listing is generated) |
| `src/algorithms/<group>/index.md` | A group of algorithm pages: `title`, `short` (sidebar label), `summary`, `order` |
| `src/algorithms/<group>/*.md` | Algorithm pages (`summary`, `complexity`, `order`) and overview pages (`kind: topic`) |
| `src/guide/index.md`, `src/guide/<group>/*.md` | User guide |
| `src/tutorials/index.md`, `src/tutorials/*.md` | Examples & tutorials (same structure as algorithms; groups optional) |
| `src/history/index.md`, `src/history/<group>/*.md` | Release notes |
| `src/references.md`, `src/references-*.md` | Bibliography: `[Key]: text` per line; all files are merged |
| `src/macros.tex` | `\newcommand`s shared by KaTeX and LaTeX |

## Page model

* Every function gets a URL. A `::: function` block in the module overview is
  the single place its prototypes are written. If a hand-written page lists the
  function under `functions:`, that page is its home; otherwise an automatic
  page is generated from the block (prototypes, overview text, the block's
  `::: details`, source links, previous/next).
* Several functions documented by one block share a page, and a hand-written
  page may claim several blocks, all from the same section of the overview.
  On such a page each block's `::: details` are shown with its own
  prototypes; the page body follows the synopsis.
* A hand-written page in a module directory without `functions:` is a
  guide: a narrative about using the module (or part of it) that is a direct
  child of the module. Guides are listed on the module page and in the
  sidebar, and every function page mentioned by a guide links back to it.
  Use a guide, not a function page, for text spanning several sections.
* Algorithm pages automatically get a "Referenced from" list of every function
  block or page that links to them.
* Module front matter: `title`, `header`, `category` (groups modules on the
  home page), `order` (position within the category), `description` (the
  text of the module's card on the home page; like `summary`, it is not
  repeated on the page itself or in the PDF), and
  optionally `extra-headers` (other modules whose headers declare functions
  documented here, e.g. `flint`), `source` (the header/source directory when
  it differs from the page directory, e.g. `gr_domains` documents `gr.h`),
  `template-headers` (headers such as `fq_poly_templates` whose expansion
  in this module's header declares its functions) and `preprocess` (sets
  of compiler flags under which the header is expanded with `$CC -E`; a set
  that fails to preprocess is reported as a warning with the compiler's
  error, since the functions it generates are then missing).
* Collections: `guide/` (User guide), `algorithms/`, `tutorials/` and
  `history/`, each with groups `<collection>/<group>/index.md`.
* `check --only fmpz_poly,algorithms/polynomials` and
  `examples --only ...` restrict reports and example runs to some paths.
* Every prototype is checked against the declaration in `src/<module>.h`
  (types only, parameter names may differ), and `check` lists public header
  functions with no documentation. Source links point at the definition
  (found by scanning `src/<module>/*.c` and the header) at the current commit.

## Markup

A strict Markdown subset plus fenced divs. No underscore emphasis, so
identifiers and math never need escaping.

````
---
title: Modular multiplication          front matter: key: value
functions: n_mulmod2_preinv n_mulmod2  (function pages)
summary: One sentence.                 (shown only on the cards linking to the page:
                                        the page's own introduction must not rely on it)
---

## Section {#optional-id}

`n_mulmod2_preinv`        code; auto-linked when it names a documented symbol
$ab \bmod n$              inline math;   $$ ... $$ display math
[](algorithms/shoup)      link with automatic text (page title / "Theorem 2" / symbol)
[text](#thm-correct)      link to a numbered block on this page
[@GraMol2010]             citation;  [@GraMon1994, §9]  with a locator

::: function
ulong n_gcd(ulong x, ulong y)          one prototype per line, then a blank line

Short description (shown on the module page and the function page).

::: details
Longer text, only on the function's own page.
:::
:::

::: type / ::: macro / ::: variable   like ::: function, for types, macros, globals

::: theorem Optional title {#thm-id}   also lemma, proposition, corollary,
:::                                    definition, remark, proof, algorithm,
                                       note, warning
::: summary algorithms/shoup :::       card linking to a page, with its summary
                                       (in the PDF, a reference to the section)
::: functions n_gcd n_xgcd :::         compact list of linked prototypes

```c example name=gcd_basic           compiled and run by `fdoc examples`
...
```
```output                              expected stdout, compared exactly
...
```
````

Output that legitimately differs between platforms can be marked on the
`output` fence (like SageMath's `# random`, `# abs tol`, `# rel tol`):

| flag | meaning |
|---|---|
| `radius-tol`, `radius-tol=F` | radii of printed balls (the number after `+/-`) may differ by a factor up to `F` (default 10); everything else exactly |
| `rel-tol=X`, `abs-tol=X` | every number may differ by this relative or absolute amount |
| `random` | not compared; the program must still compile and run |

The text between the numbers, the number of lines and the number of numbers
must still match. Ball radii are rigorous but not reproducible bit for bit:
they can depend on the compiler (e.g. on whether it contracts expressions
into fused multiply-adds) and on the algorithms selected for the machine.
Prefer an output that is reproducible (print fewer digits, test a property
instead of printing a radius) and use these flags only where the varying
numbers are what the example is about. The pages show a short note next to
such an output.

## Library defects found while documenting

Do not fix library code as part of documentation work: report the defect
(see the User guide page on reporting bugs) and, until it is fixed,
describe it on the affected documentation page.
